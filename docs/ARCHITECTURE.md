# Архитектура и решения

Один Next.js App Router проект: витрина, серверные API и Payload /admin. PostgreSQL хранит контент, настройки, заказы и журнал CRM. Доменные функции расчёта не зависят от CMS или модели.

## Цена
Вход: десятичная строка исходной цены, положительный курс KZT за 1 единицу, исходная ставка НДС и флаг включения, целевая ставка НДС. Если НДС включён, сначала исключаем исходный НДС, затем конвертируем и добавляем целевой. Промежуточные значения не округляем; итог за единицу — вверх до целого KZT (решение владельца 08.10.2026, как на старом cad.kz). Сумма строки = округлённая цена единицы × целое количество 1–999. НДС внутри итоговой цены выделяется до 0,01 KZT. НДС внутри цены выделяется по правилу HALF_UP. 16% — настройка из брифа, не заключение о налоговых обязанностях.

Клиент передаёт только ID предложения и количество. Сервер загружает опубликованное предложение, курс и ставки. Присланные клиентом цены игнорируются. Перед подтверждением заказа пересчёт; при изменении — повторное подтверждение. В заказ сохраняются неизменяемые строки с названием, комплектацией, исходной ценой/валютой, курсом/датой, ставками, итогом и версией правила.

## Модель данных
Users (admin/editor), Products, Offers, Sections (parent/direction), Manufacturers, Media, Publications (article/news/promotion), Courses/Services через тип товара, ExchangeRates (история), PricingSettings, Orders, Conversations, CRMDeliveries, Redirects, ImportRuns.
Legacy key: source + entity type + old ID; уникален и индексируется. Предложения связаны с продуктом; продукт хранит направления, задачи, характеристики, рекомендации и зависимости. Зависимости должны проверяться на сервере, включая наличие базы у клиента.
Публичное чтение только опубликованного контента. Запись контента и добавление нового курса валют — редактор/администратор (маркетологи сами обновляют курс; прошлые записи курса не правятся, чтобы рассчитанные цены оставались проверяемыми). Пользователи, ставка НДС и интеграции — администратор. Заказы/переписка не доступны публично. Публичное создание заказа — только специализированным валидируемым API.

Каталог по CRM (12.10.2026): у раздела может быть «Родительский раздел» — подраздел не показывается в меню, фильтре и на главной, его товары видны в родителе (`src/domain/sectionTree.mjs`, сворачивание в `src/lib/catalog.ts` и `src/lib/navigation.ts`); подборки «Похожие» и «С этим покупают» по-прежнему работают по своим разделам. Программа с основным разделом оборудования (ReCap, Geomagic в «3D-сканировании») попадает в группу «Оборудование». «Сценарий покупки» — у раздела (по умолчанию) и у товара (свой): стандартная лицензия, корпоративное ПО, оборудование, продление, услуга; от него кнопки страницы товара и карточки (`src/domain/buyScenario.mjs`). Сценарий раздела, не подходящий типу товара, пропускается (оборудование у программы — стандартная лицензия).

## ИИ и CRM
Интерфейс адаптера модели принимает сообщения и инструменты searchProducts/searchPriceList/getPrice/priceTotal/handoffToManager (с 13.10.2026; раньше getOffers/quote). Ответы getPrice и priceTotal авторитетны: модель не вычисляет цены. Демонстрационный адаптер обязан обозначать отсутствие подключённого ИИ. Ограничения длины, rate limits, таймауты, санитарная обработка контента и логирование без секретов обязательны до публикации.
После явного согласия клиента транзакция PostgreSQL сохраняет заявку и outbox с уникальным ключом идемпотентности. Worker обрабатывает очередь с блокировкой, backoff и dead-letter. На неоднозначном таймауте сначала сверяет внешний ID в CRM; слепой повтор создания запрещён. Exactly-once между системами без сверки не обещаем. Тестовый адаптер не вызывает сеть. С 20.10.2026 при вписанном `BITRIX24_WEBHOOK_URL` работает настоящий адаптер (`src/domain/bitrix24Client.mjs` — вызовы и сверка, `src/lib/crm/gateway.ts` — выбор адаптера, `src/lib/crm/pass.ts` — передача после сохранения и дослать отложенные): поиск лида по ключу, `crm.lead.add`, `crm.lead.productrows.set`; страница админки «Битрикс24» — проверка прав, тестовый лид, очередь.
Каждая заявка передаёт источник: нажатую кнопку, товар, его основной раздел и сценарий покупки (`source` в лиде; у заказа из корзины — раздел и сценарий у каждой строки, `src/lib/orderContext.ts`). В Битрикс24 источник идёт в «Дополнительно об источнике» (`SOURCE_DESCRIPTION`) и строкой в комментарий: без этого анализ сделок упирается в тег «Другое» и продления, не видные по названию. Подпись кнопки приходит от браузера только как текст до 60 знаков, раздел и сценарий сервер берёт из базы.
Менеджеры работают только в Битрикс24, в CMS они не заходят. Поэтому лид должен содержать всё: контакты, организацию и БИН, товары с комплектацией, лицензией и ценами, комментарий и историю диалога с ИИ-консультантом. Диалог с консультантом ведётся так, чтобы клиент, задав вопрос на сайте, получил в Битрикс24 лид, где разговор продолжается (открытые линии, коннектор чата), менеджер видит всю переписку и может вступить в разговор. Способ подключения (открытая линия или собственный коннектор) выбираем на этапе ИИ после проверки доступов к cadkz.bitrix24.kz.

## Поиск и будущий помощник (10.10.2026)
Пять частей, разделённых по файлам, а не отдельные сервисы:
- **Search UI** — поле в шапке и подсказки: `SiteSearch` (широкое поле в первой строке шапки от 640 px, на телефоне лупа и слой на весь экран), подсказки по группам (`groupSuggestions`) и выделение совпадения (`markMatches`) — в `src/domain/suggest.mjs`, `SearchBox` (комбобокс, клавиатура), `SearchSuggestions`, страница `/search`. Данные получает только через `/api/search?q=` (подсказки) и `searchCatalog` (страница), о базе не знает.
- **Search Service** — чистая логика без базы и сети: `src/domain/search.mjs` (совпадения: регистр, кириллица/транслит, раскладка, опечатки, основа слова, другие названия из админки; служебные слова выбрасываются, общие — «программа», «расчёт», «обновить», А0 — необязательны; места по весу: название, разделы товара, программы в составе, анонс и задачи, описание; не нашлись все слова — похожие с пометкой `partial`) и `src/domain/suggest.mjs` (что и в каком порядке показать, одна строка на семейство). Тесты `tests/search.test.mjs`, `tests/suggest.test.mjs`, набор запросов покупателей `tests/searchQueries.test.mjs`.
- **Integration Layer** — `src/lib/searchIndex.ts`: индекс из Payload (товары, семейства, производители, разделы, страницы), минуту в памяти сервера. Разделы, состав подбора и семейства, описание и характеристики для поиска — `src/lib/searchText.ts` (в карточки каталога не попадают, страницы не тяжелеют). Каталог попадает в Payload импортом из Битрикса (`/admin/import-bitrix`); живого обмена с Битриксом нет. Сменится источник — меняется только этот файл.
- **Assistant UI** (12.10.2026) — `Assistant` (голова Юки в шапке на телефоне, от 640 px Юки-буханка в углу экрана — `AssistantLauncher` — и окно на её месте; открыть из страницы — `openAssistant()` в `src/lib/openAssistant.ts`), `AssistantPanel`, `AssistantMessages`, `AssistantComposer`, `AssistantHandoff`, состояние — `src/lib/useAssistant.ts` (копия разговора в sessionStorage, переход по страницам его не теряет); поиск в шапке от него не зависит. Можно отключить, не мешает кнопкам, ценам и полям. Персонаж — Юки (12.10.2026): голова и позы в `Mascot`, шапка окна «Юки · ИИ-консультант CAD.kz» — `AssistantHeader`. Приветствие (с правилами владельца, 13.10.2026): «Привет! Я Юки из CAD.kz. Подберу программу и цену. С чего начнём?», быстрые действия: «Подобрать программу», «Узнать стоимость», «Продлить лицензию» (и любой вопрос со словом «продл…» — под ответом ссылка на форму `/renew`), «Найти оборудование», «Связаться с менеджером» (открывает передачу менеджеру в Битрикс24, там же кнопка WhatsApp). Кнопка запуска и окно появляются на сайте только вместе с работающим Assistant Service: пустышек и имитации ответов нет, окно само не открывается (только реплика «Помочь с выбором?» у Юки раз за посещение).
- **Проверка Юки** (13.10.2026) — админка → «Проверка Юки» (`/admin/assistant-check`, администратор и маркетолог): типичные вопросы по одному в строке (стартовый список — `CHECK_QUESTIONS` в `src/domain/assistantCheck.mjs`, свой список запоминается в браузере), ответы по очереди тем же путём, что на сайте (`answerMessages` в `service.ts`), но без сохранения разговора; под ответом обращения к инструментам и флаги `checkReply`: цена, которой нет в ответах инструментов, сроки, нормы, «заявка оформлена», род о себе, эмодзи, Markdown. Отчёт — CSV для Excel. API — `POST /api/admin/assistant-check`.
- **Assistant Service** (12.10.2026) — `POST /api/assistant` (`src/lib/assistant/`): режим по `MODEL_PROVIDER` (`provider.ts`: anthropic — Claude через Messages API, `src/domain/anthropicChat.mjs`, сеть без SDK; demo — без модели, честная пометка и поиск по каталогу; off/пусто вне демо — выключен, кнопки нет). Правила модели, лимиты, проверка сообщения и история — `src/domain/assistant.mjs`. История разговора — только на сервере (журнал «Диалоги консультанта», `conversation.ts`): браузер присылает ключ разговора и новое сообщение, поэтому подставить «ответ Юки» нельзя, а в лид уходит ровно то, что видел клиент. Лимиты: 1000 знаков сообщение, 20 вопросов в разговоре, 10 сообщений в минуту с адреса, модели — последние 16 сообщений, до 6 кругов обращений к инструментам за ответ, ответ ждём 30 с. В журнал ошибок — только вид ошибки и код, без текста и ключа. Передача менеджеру — та же заявка `/api/request` (источник `assistant`, тип «Консультация», ключ разговора): переписку сервер берёт из журнала, кладёт в лид и отмечает разговор «передан» с номером заявки. Инструменты модели (13.10.2026): `searchProducts` = тот же поиск, что на странице `/search` (`searchCatalog`, до 6 товаров, без цен — для подбора и ссылок); `searchPriceList`, `getPrice`, `priceTotal` = прайс компании «Прайс CAD.kz» (лист product_price_list), загруженный в админке «Прайс и база Юки» (коллекция `price-tables`, одним снимком, в памяти сервера с индексом; `src/domain/priceTable.mjs`, `src/lib/assistant/priceTable.ts`): поиск отдаёт строки без цен, цену — только `getPrice` по коду и только для новой лицензии ПО с числовой ценой, срок поставки — по условиям компании; `handoffToManager` — данные для передачи менеджеру (имя, телефон, почта, компания, продукт, сроки): кнопка под ответом открывает форму с подставленными данными, клиент подтверждает и даёт согласие сам, собранное уходит в комментарий и почту лида с сервера (снимок разговора), а не из браузера. Правила — правила владельца (13.10.2026) с характером Юки поверх и база знаний (коллекция `assistant-knowledge`, лист FAQ) — двумя частями: постоянная кешируется у Anthropic (`cache_control`), состояние разговора (время Астаны, рабочие часы, прайс, передача) — каждый раз. Цены, состав и совместимость модель берёт только из ответов инструментов, сама не придумывает. Итог разговора — заявка `/api/request` с диалогом в лиде Битрикс24.

Схема: поле поиска → `/api/search` → suggest → индекс → Payload ← импорт из Битрикса. Помощник → свой API → модель ↔ инструменты (тот же индекс, pricing) → ответ; передача менеджеру → лид Битрикс24.
Помощник для админки (черновики описаний, неполные карточки) — только через права Payload (`src/cms/access.ts`), изменения цен и товаров — черновиком с подтверждением человека.

## Импорт
Сначала dry-run и отчёт по количествам/ошибкам. Upsert по legacy key, затем связи вторым проходом. Медиа дедуплицируются по checksum, исходные URL сохраняются. Никаких удалений отсутствующих записей по умолчанию. Старые адреса в Redirects, конфликты ручной правки фиксируются. Числа из брифа сверяются с экспортом.

## Инфраструктура
Отдельный домен/поддомен и БД, TLS, резервные копии БД и медиа, проверка восстановления, ограниченный доступ к админке, журнал ошибок и health checks. Миграции выполняются явно; автоматическое изменение production-схемы запрещено. Срок хранения контактов и переписки согласовать до публичного сбора.


## Навигация каталога (26.10.2026, вариант Codex)
`getMenu` и `getMenuPopular` используют `getCatalog` (React cache в пределах запроса). Меню и страница применяют одни функции `results`, `facetOptions`, `update` из `catalogFilter.ts`; промежуточных экранов с производителями нет. Данные Payload и серверный расчёт цен не менялись. Старые query-параметры сохраняются; `browseState` определяет вкладку старого адреса без `group`, а пустой адрес открывает популярные. `pushState` и `popstate` сохраняют последовательность выбора.

`catalogPresentation.mjs` определяет тип карточки по уже имеющимся данным и содержит проверенную справку о трёх коллекциях Autodesk (источники и дата сверки в файле). Это слой показа, без записи в общую базу. Для редакторского контроля позже стоит добавить поле «Вид товара»: программа / коллекция / модуль / нормативная база; вид линейки уже известен по её связи, курс и оборудование — по `kind`. Также полезны поля состава коллекции, официального источника и даты проверки. Миграции и catalog-setup в этой ветке не нужны.
