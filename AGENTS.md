# Новый сайт CAD.kz — правила проекта

Прочитать перед работой: `docs/BRIEF.md` (задача), `docs/ARCHITECTURE.md` (решения), `docs/DESIGN.md` (дизайн-система), `docs/PLAN.md` (этапы). Владелец проекта — маркетолог, не программист: объяснять результат простыми словами и давать ссылку на работающий сайт (превью), а не код. Скриншоты владельцу не присылать: он смотрит на самом сайте.

## Обязательная проверка

Перед каждым коммитом: `pnpm format`, затем `pnpm check` (Biome, дизайн-система, типы, тесты). Коммит с красной проверкой запрещён. Для изменений вёрстки — самому проверить страницу в Playwright на 1440 и 390 px (скриншоты для себя, владельцу не отправлять).

## Дизайн

- Все цвета, кегли, начертания, скругления, тени, z-index — только `var(--…)` из `src/styles/tokens.css`. Скрипт `scripts/check-styles.mjs` ловит нарушения.
- Брейкпоинты только 640 / 960 / 1200, mobile-first через `min-width`.
- Шапка, меню и подвал — по одному общему компоненту на весь сайт, в `src/app/(site)/layout.tsx`, ширина всегда `--container`. Страницы не делают свою шапку и не меняют её ширину.
- Ширина: одна рамка `--container` на всех страницах, общий левый край с логотипом. Каждая страница — по одному из четырёх шаблонов из `docs/DESIGN.md` (Витрина, Каталог, Товар, Чтение). Блоки занимают целое число колонок 12-колоночной сетки, абзацы не шире `--measure`. Узкие колонки по центру не делаем, в том числе для текстов: шаблон «Чтение» — текст слева, справа колонка навигации.
- Точность до пикселя: только целые px из токенов, никаких 801/803 и дробных значений. Ширины блоков — производные рамки и сетки, а не подобранные на глаз. После вёрстки страницы проверить в Playwright на 1440, 1200, 960, 640 и 390 px: рамка ровно `--container` (или ширина экрана минус два `--gutter`), левый край шапки, контента и подвала совпадает, горизонтальной прокрутки нет.
- Заголовки сдержанные: h1 не больше 30 px, h2 не больше 24 px (токены `--text-display`, `--text-h2`).
- Нет нужного значения — сначала добавить токен и строку в `docs/DESIGN.md`, потом использовать.
- Макеты в `Макеты/` — референс композиции, а не источник значений. Их логику (расчёт цены в браузере, фейковые ответы чата, успешная отправка без запроса) не переносить.
- Иконки — только `lucide-react` (16/20/24, strokeWidth 1.75). Картинки — `next/image`.

## Код

- TypeScript strict. Без `any`, без `!`, без `@ts-ignore`. `biome-ignore` — только с объяснением причины.
- Один компонент — одна папка: `src/components/<Name>/<Name>.tsx` + `<Name>.module.css`. Стили компонента только в его CSS-модуле. Без inline-style, без глобальных классов для компонентов, без CSS-фреймворков и UI-китов.
- Серверные компоненты по умолчанию. `'use client'` — только для интерактива и как можно ниже по дереву.
- Компонент больше ~150 строк или с несколькими обязанностями — разделить.
- Данные страниц — из Payload на сервере (`src/lib/`), не захардкоженные массивы в компонентах. Демоданные — только в `src/domain/demo.ts` и только в `APP_MODE=demo`.
- Деньги: только серверный расчёт через `src/domain/pricing.mjs` (точная арифметика, цена за единицу вверх до целого тенге). Клиент передаёт ID предложения и количество, цены от клиента игнорируются.
- Конфигурация CMS — в `src/cms/` (коллекции по файлам, общие поля в `fields.ts`, права в `access.ts`). `payload.config.ts` только собирает их.
- Секреты — только в `.env`, никогда в коде, коммитах и переписке.
- Новая зависимость — только если без неё никак; точная версия в `package.json`, причина в описании коммита.
- Имена: компоненты PascalCase, файлы утилит camelCase, CSS-классы camelCase в модулях. Комментарии и тексты интерфейса — на русском.

Старая вёрстка прототипа перенесена и удалена (08.10.2026), `LEGACY_FILES` в `scripts/check-styles.mjs` пуст — новых исключений не добавлять.

## Скорость

- Цель для каждой страницы: LCP < 2.5 с и CLS < 0.1 на мобильном.
- Шрифты локальные, только latin + cyrillic. Картинки с размерами, `priority` только у первой картинки экрана.
- Клиентский JS минимален: никаких библиотек анимаций, каруселей и состояния без согласования.

## Git

- Работа в `main` небольшими коммитами. Сообщение на русском: что изменилось и зачем.
- Не коммитить `.env`, `media/`, сборки. `payload-types.ts` генерируется Payload и коммитится.

## Работа по чатам и модель

- Состояние проекта и ближайшие шаги лежат в `docs/HANDOFF.md`. В начале нового чата прочитать `AGENTS.md` и `docs/HANDOFF.md`, в конце каждого этапа обновить `docs/HANDOFF.md` и закоммитить.
- Следить за объёмом контекста. Когда накопилось много (длинная переписка, много прочитанных файлов и логов, началось сжатие истории) или этап закончен, прямо написать владельцу: «Следующий шаг лучше начать в новом чате», назвать рекомендуемую модель и дать готовый текст для вставки в новый чат.
- Рекомендация по модели: архитектура, ИИ-консультант, интеграция с Битрикс24, сложные ошибки — Opus 5.5 с высоким уровнем рассуждений (high); обычная вёрстка, контент, мелкие правки — Opus 5.5 medium. Sonnet годится только для простых мелочей.
- Модель выбирается в самом приложении до начала чата, сменить её изнутри чата ассистент не может. Если задача сложнее, чем подходит текущая модель, сказать об этом.
- Готовый текст для нового чата: «Продолжаем сайт CAD.kz (репозиторий Cadkz/cad.kz). Прочитай AGENTS.md и docs/HANDOFF.md, затем продолжай с пункта «Следующий шаг». Я не программист, объясняй простыми словами, скриншоты не присылай, давай ссылку на сайт.» В тексте указать конкретный следующий шаг из `docs/HANDOFF.md`.
